# Task 1. Реестр транзакций Saga-оркестрации OrchestrPay

## Контекст

Платёж на маркетплейсе: инициация → списание средств → проверки (FraudCheck, AML/GeoRisk)
→ перевод контрагенту → уведомления. Оркестрация — Camunda BPMN, состояние саги хранится
в PostgreSQL, промежуточные статусы и результаты внешних проверок кэшируются в Redis.

## Реестр транзакций Saga

| # | Транзакция | Описание | Тип | Компенсация |
|---|------------|----------|-----|-------------|
| 1 | `CREATE_PAYMENT` | Создание агрегата платежа в Payment Service (PostgreSQL): `paymentId`, `idempotencyKey` от маркетплейса, сумма, мерчант, клиент; статус `CREATED`. Локальная ACID-транзакция. | компенсируемая | `CANCEL_PAYMENT` |
| 2 | `DEBIT_FUNDS` | Списание средств со счёта клиента через платёжный шлюз/банк; фиксация статуса `DEBITED`, запись в журнал операций. Внешний вызов с идемпотентным ключом. | компенсируемая | `REFUND_FUNDS` |
| 3 | `FRAUD_CHECK` | Проверка в FraudCheck Service (внутренние правила) и внешних провайдерах (AML, GeoRisk). Ответ: `ALLOW` / `DENY` / `MANUAL_REVIEW`. Таймауты, retry с экспоненциальной задержкой, идемпотентность по `paymentId`, кэш результатов в Redis. При отсутствии ответа по истечении cut-off-time — по умолчанию `ALLOW`. | повторяемая | — |
| 4 | `AWAIT_MANUAL_REVIEW` | Состояние ожидания решения оператора (не более 20 минут): таймер Camunda + опрос статуса ручной проверки. По истечении 20 минут — cut-off → `ALLOW`. | повторяемая | — |
| 5 | `TRANSFER_TO_COUNTERPARTY` | Перевод средств контрагенту (мерчанту) через платёжный шлюз; фиксация статуса `TRANSFERRED`. **Точка невозврата (pivot)**: после успешного перевода сага обязана завершиться успехом. | необратимая | — (в рамках саги; пост-фактум — отдельный процесс возврата/чарджбэка) |
| 6 | `NOTIFY_CLIENT` | Уведомление клиента о статусе операции через Notification Service (at-least-once, дедупликация по `eventId`). | повторяемая | — |
| 7 | `NOTIFY_SECURITY` | Уведомление службы безопасности о подозрительной/заблокированной операции для анализа. | повторяемая | — |
| 8 | `COMPLETE_PAYMENT` | Фиксация финального статуса `COMPLETED` в PostgreSQL, публикация события `PaymentCompleted` (transactional outbox). | повторяемая | — |

## Компенсирующие транзакции

| Транзакция | Описание | Тип | Компенсация |
|------------|----------|-----|-------------|
| `CANCEL_PAYMENT` | Перевод платежа в статус `CANCELLED`, фиксация/освобождение idempotency-ключа. Идемпотентна, ретраи до успеха. | повторяемая (компенсирующая) | — |
| `REFUND_FUNDS` | Возврат списанных средств клиенту через платёжный шлюз, статус `REFUNDED`, событие `PaymentRefunded`. Выполняется автоматически, без участия поддержки; идемпотентна по `refundId`, ретраи до успеха. | повторяемая (компенсирующая) | — |

## Порядок выполнения и компенсации

1. `CREATE_PAYMENT` → 2. `DEBIT_FUNDS` → 3. `FRAUD_CHECK` (при `MANUAL_REVIEW` — 4. `AWAIT_MANUAL_REVIEW`)
   → 5. `TRANSFER_TO_COUNTERPARTY` → 6. `NOTIFY_CLIENT` → 7. `COMPLETE_PAYMENT`.

- **Успех**: проверка вернула `ALLOW` (или сработал cut-off) → деньги переводятся контрагенту.
- **Запрет** (`DENY` от antifraud или оператора): компенсация в обратном порядке —
  `REFUND_FUNDS` → `CANCEL_PAYMENT`, параллельно `NOTIFY_CLIENT` (клиенту) и `NOTIFY_SECURITY` (в службу безопасности).
- **Сбой/таймаут на любом шаге до pivot**: Camunda по сохранённому в PostgreSQL состоянию
  саги повторяет шаг (если он повторяемый) либо запускает компенсации в обратном порядке.
